一、系统总体架构

平台采用分层微服务架构，自顶向下分为五层：

┌──────────────────────────────────────────────────────────────────────┐
│  接入层  Web 门户 / 大屏(IOC) / 移动端(App·小程序) / 企业端 / 监管端        │
├──────────────────────────────────────────────────────────────────────┤
│  网关与安全层  Spring Cloud Gateway + OAuth2.1/OIDC + WAF + 限流熔断      │
├──────────────────────────────────────────────────────────────────────┤
│  应用微服务层  按业务域拆分（安环、应急、设备、人员定位、能碳、运营等）      │
├──────────────────────────────────────────────────────────────────────┤
│  共享支撑层  告警引擎 / 规则引擎 / 工作流 / 视频AI网关 / GIS空间服务 /       │
│            通知服务(短信·语音·广播·PUSH) / 文件服务 / 融合通信            │
├──────────────────────────────────────────────────────────────────────┤
│  数据中台层  采集接入 → Kafka → 实时计算(Flink) → 时序库/数仓 → 主数据     │
├──────────────────────────────────────────────────────────────────────┤
│  基础设施层  K8s / Nacos / Sentinel / Prometheus / ELK / Seata / MinIO   │
└──────────────────────────────────────────────────────────────────────┘

设计原则

  • 每个微服务独立数据库、独立部署、单一职责（Database-per-Service）。
  • 高频监测与应急指挥链路独立隔离，避免被日常流量拖垮。
  • 聚合展示（IOC 大屏）作为 CQRS 读侧，不持有业务真相源。

二、微服务模块划分

按业务域驱动设计（DDD）拆分为 14 个服务，各服务私有数据相互独立。

2.2 核心模块职责边界说明

  • 安环管理（safety-svc + env-svc）：safety-svc 负责安全合规（风险、隐患、作业票、一企一档）；env-svc 负责环保全过程监管（排口、VOCs、固废联单）。两者共享主数据与设备，但数据真相源隔离。
  • 应急指挥（emergency-svc）：平急结合指挥中枢，独立高可用部署单元。日常维护预案与资源，应急时接管调度，对其他服务仅做降级容错调用（超时即走本地预案基线），保障"黄金十分钟"调度不依赖外部可用性。
  • 设备管理（device-svc）：统一管理传感/视频/定位/门禁/无人机资产，提供设备健康度给 monitor/env/corridor 复用，避免各域重复建设备表。
  • 人员定位（closedmgmt-svc）：集成 UWB/蓝牙/GPS 定位，承载出入园管控、人员实时位置、电子围栏越界、SOS 求助，并向应急指挥提供实时位置共享。
  • 重大危险源监测（monitor-svc）：独立于安全台账，单独库 + 读写分离，10s 刷新（PRD 性能要求），不被低频查询拖累。
  • 智能运营中心（ioc-svc）：CQRS 读模型，订阅事件 + 主动拉取组装大屏，不反向写业务，保证 30s 刷新与 ≤5s 加载。

三、服务间通信机制

3.1 通信方式选型

场景 方式 说明
实时请求/响应（页面查询） OpenFeign（同步 REST） 经 Gateway，带链路追踪
跨域事件通知（预警、告警、事件） Kafka 异步事件 解耦、削峰、可重放
实时流式数据（IoT 点位） Kafka + WebSocket 推送 iot-ingest → monitor/env/energy/device
大屏聚合 ioc-svc 主动拉取 + 订阅告警事件 CQRS 读模型

3.2 关键调用链

① 设备数据：企业DCS/PLC → iot-ingest-svc → Kafka{topic: iot.raw}
        → monitor-svc / env-svc / energy-svc / device-svc(状态)

② 预警闭环：monitor-svc 超阈值 → AlarmEvent(Kafka)
        → 告警引擎(分级) → notification-svc(推送)
        → ioc-svc(聚合展示) / emergency-svc(达应急等级) / 移动端(H2 PUSH)

③ 应急联动：closedmgmt-svc(车辆越界/SOS) → EmergencyTriggeredEvent
        → emergency-svc(接处警+资源推荐) → notification-svc(多通道调度)
        → closedmgmt-svc(位置共享) / ioc-svc(大屏切应急模式)

④ 作业票联动：safety-svc(特殊作业提交) → 调 device-svc(气体传感器)
        + monitor-svc(实时值) + 视频AI网关(现场画面) 联合抽查

⑤ 封闭化联动安全：closedmgmt-svc 黑名单拦截 → AlarmEvent → notification-svc + 安保

3.3 调用约束

  • 禁止循环调用：业务服务 → ioc-svc 只能"拉"（ioc 不反向写业务）。
  • 应急优先：emergency-svc 跨服务调用均带熔断降级与本地缓存兜底。
  • 跨域只读：operation-svc / ioc-svc 跨域查询走 Feign + Sentinel 熔断，失败返回兜底数据。

四、API 网关设计

采用 Spring Cloud Gateway 作为统一入口。

4.1 核心职责

  • 统一路由：按路径/服务名路由至后端微服务（如 /api/safety/** → safety-svc）。
  • 统一鉴权：校验 OAuth2.1 Access Token，解析身份与权限范围（模块/功能/数据级）。
  • 限流熔断：基于 Sentinel 的网关流控（按 IP/用户/API 维度），防止恶意刷量或雪崩。
  • 灰度发布：基于请求头/用户标签的权重路由，支持小流量验证新版本。
  • 日志审计：记录入口请求（脱敏），对接 ELK。
  • 协议转换：对外暴露 HTTPS/REST，内部可转发 gRPC（AI 推理等）。

4.2 网关路由示例

路由前缀 目标服务 鉴权 限流
/api/iam/** iam-svc 部分公开(登录) 中
/api/safety/** safety-svc 必需 中
/api/monitor/** monitor-svc 必需 高(实时)
/api/emergency/** emergency-svc 必需 高(应急优先)
/api/closed/** closedmgmt-svc 必需 中
/api/env/** env-svc 必需 中
/api/energy/** energy-svc 必需 低
/api/operation/** operation-svc 必需 中
/api/ioc/** ioc-svc 必需 高(大屏)

4.3 容错

  • 网关层超时 < 后端服务超时；后端不可用时返回标准化错误与兜底提示。
  • 紧急态下 emergency-svc 路由标记 最高优先级，资源倾斜。

五、服务注册与发现

采用 Nacos 作为注册中心（同时承担配置中心，见第六节）。

5.1 机制

  • 所有微服务启动时向 Nacos 注册实例（IP + 端口 + 元数据：环境/版本/健康权重）。
  • 客户端（OpenFeign + LoadBalancer）从 Nacos 拉取服务列表，配合本地缓存 + 健康检查实现故障自动剔除。
  • 支持临时实例（心跳保活）与持久实例（防止注册中心抖动导致大规模下线）。

5.2 高可用

  • Nacos 集群部署（≥3 节点），Raft 一致性协议。
  • 注册中心不可用时，服务依赖本地缓存继续运行（降级），不影响已建立的调用。

六、配置中心

采用 Nacos Config 统一管理配置。

6.1 配置组织

  • 按环境隔离：dev / test / prod 命名空间（Namespace）。
  • 按服务分组：每个微服务独立 Group（safety-svc、monitor-svc …）。
  • 配置格式：YAML，支持动态刷新（@RefreshScope）。

6.2 典型配置项

  • 数据源、Kafka 地址、Redis 地址、Sentinel 规则。
  • 业务参数：告警阈值、通知方式、数据刷新频率（对应 PRD G4 系统参数配置）。
  • 等保相关：TLS 开关、审计级别、密码策略。

6.3 敏感配置

  • 数据库密码、第三方 Key 经 Nacos 加密插件（AES）存储，禁止明文入库。
  • 配置变更留痕，支持版本回滚。

七、数据存储方案

按"业务库 + 时序库 + 缓存 + 消息 + 对象存储"多引擎组合。

7.1 存储分层

数据类型 存储引擎 用途
业务关系数据（企业/隐患/作业票/预案） PostgreSQL 14 主业务库，每服务独立 Schema/库
时序数据（IoT 点位、能耗、环保监测） TimescaleDB（PostgreSQL 扩展） 高频写入、时间窗口聚合、历史回溯
缓存/会话/热点 Redis 7 会话、设备在线状态、大屏聚合缓存
消息/事件流 Kafka 3.x 解耦、削峰、事件溯源
文件/视频/图片 MinIO（对象存储） 抓拍图、巡检报告、预案附件、视频片段
日志 Elasticsearch（ELK） 操作审计、应用日志检索

7.2 多租户与隔离

  • 单园区私有化部署：按 Schema 隔离（每园区/企业独立 Schema + 行级数据权限）。
  • SaaS 多园区：按 数据库实例隔离 + 行级过滤（JDBC Filter 自动注入 tenant_id）。

7.3 数据一致性

数据类别 一致性要求 方案
主数据(园区/企业/危险源) 强一致、低频变更 mdm-svc 单一真相源，其他域订阅快照到本地读模型
IoT 实时点位 最终一致、可重传 Kafka 持久化 + 至少一次；时序库幂等写入
告警/预警/应急事件 不丢、有序 Kafka 分区键(设备ID/事件ID)保序 + 落库确认
隐患/作业票/审批 强一致 + 审计 单服务本地事务；跨服务用 Seata Saga/TCC
跨域统计(IOC/经济运行) 最终一致 事件溯源 + 定时核对

7.4 分布式事务（Seata）

  • Saga 模式：长流程（特殊作业审批→气体检测→视频抽查→批准），每步有补偿。
  • TCC 模式：资源类（应急资源调度锁定：预留→确认/取消）。
  • 幂等：所有 Kafka 消费者按 eventId 幂等；IoT 点位带 timestamp+deviceNo 去重。
  • 状态机：隐患/作业票流转用 Spring Statemachine 防非法跃迁。

7.5 备份策略

  • 每日全量备份 + 实时增量（WAL 归档）；备份加密存储于对象存储异地副本。
  • 故障恢复时间目标（RTO）≤ 30min，RPO ≤ 5min。

八、部署架构

8.1 容器化与编排

  • 所有微服务打包为 Docker 镜像，由 Kubernetes 编排部署。
  • 使用 Helm Chart 统一管理发布，支持按园区一键部署。
  • 关键服务（monitor / emergency / ioc）配置 Pod 反亲和 + 多副本 + HPA 自动扩缩容。

8.3 高可用与可靠性

  • K8s 多节点集群，控制面与工作负载分离。
  • 中间件均集群化：Nacos(≥3)、Kafka(≥3 broker + 副本)、PostgreSQL(流复制/Patroni)、Redis(哨兵/集群)。
  • 7×24h 运行，年意外宕机 ≤ 3 次，操作失败率 < 0.5%。

8.4 边缘层

  • 园区现场部署边缘网关（iot-ingest 轻量版），断网期间本地缓存数据，恢复后补传 Kafka，保障采集不丢。

九、安全策略

满足 GB/T 22239-2019 等保 2.0 三级要求。

控制项 实现方案
传输加密 Gateway 全链路 TLS 1.3；内部服务间 mTLS
存储加密 敏感字段 AES-256（证照、位置、视频元数据）；数据库透明加密(TDE)
身份认证 iam-svc：OAuth2.1 + OIDC；移动端 PUSH 令牌绑定设备
访问控制 三级 RBAC：模块级 / 功能级 / 数据级（按企业 ID 行级隔离，多租户）
审计留痕 操作日志只追加(WORM)，不可删除；ELK 归档，记录操作人/时间/IP/内容
多租户隔离 按园区隔离；企业用户仅见本企业数据（数据级权限 + 行级过滤）
入侵防护 WAF + Sentinel 限流熔断 + 黑名单联动（closedmgmt 触发）
可用性 K8s 多副本 + 反亲和；日全量 + 实时增量备份；RTO ≤ 30min
视频安全 GB/T 28181 联网，视频流经网关鉴权，抓拍图落 MinIO 加密

应急场景安全：emergency-svc 独立资源配额，应急模式下优先级最高，调度链路不依赖外部服务可用性。

Accept-Language 否 zh-CN / en-US

pageNum(默认1) / pageSize(默认20) / sort(如 createdAt,desc)；响应含 total、pages、list。

1.4 公共错误码语义

  • 作业票审批冲突 → 40902

3.3 分区与保序策略

  • 保序维度：以 deviceNo / refId / hazardId 作为分区键（Partition Key），保证同一设备/同一隐患的事件严格有序。
  • 幂等消费：所有消费者按 eventId 去重（Redis/本地表），重复投递安全。
  • 至少一次投递：Producer 开启 acks=all + 重试；消费者先落库再提交 offset。
  • 死信队列：消费失败超阈值进入 *.DLT 主题，告警人工介入。
  • Schema 演进：事件体采用向后兼容扩展（新增字段带默认值），禁止修改/删除既有字段语义。

第四部分 版本与兼容策略

  • API 版本：路径携带主版本（如 /api/safety/v1），破坏性变更升主版本，新旧并行一个发布周期。
  • 事件 Schema：遵循向后兼容（additive-only），消费方忽略未知字段；重大变更发新 Topic（如 alarm.event.v2）。
  • 契约测试：各服务 REST 契约经 Spring Cloud Contract / OpenAPI 校验，CI 阶段拦截不兼容变更。
  • 网关兼容：Gateway 按 Accept-Version 头或路径路由到对应版本实例，支持灰度。

一、为什么用 Saga

特殊作业票审批是跨多服务、长周期、可补偿的业务：

  • 提交作业票（safety-svc 本地事务）
  • 联动查询气体检测实时值（device-svc + monitor-svc）
  • 联动视频 AI 抽查（视频网关）
  • 园区审核（人工，可能耗时数小时）
  • 批准作业（状态变更）

若用 2PC（XA）会长时间锁资源、拖垮高频监测库。Saga 以"本地事务 + 前向/补偿"方式，保证最终一致且不长期持锁，符合化工园区"审批可驳回/可退回修改"的业务现实。

二、作业票审批流程定义

[Submit] ──→ [GasCheck] ──→ [VideoCheck] ──→ [Review] ──→ [Approve]
   │             │                │               │            │
   └─补偿:        └─补偿:           └─补偿:          └─补偿:       └─补偿:
   rollbackDraft  clearGasHold     clearVideoHold   rejectToDraft revertApprove
步骤 服务 本地事务 补偿动作
Submit safety-svc 插入作业票 SUBMITTED 置 DRAFT / 逻辑删除
GasCheck device/monitor 记录气体检测快照、占用传感器查询会话 释放查询会话、标记快照失效
VideoCheck 视频网关 创建抽查任务、截图 取消任务、删除临时截图
Review safety-svc 状态 REVIEWED/REJECTED 回退 SUBMITTED
Approve safety-svc 状态 APPROVED，作业生效 回退 REVIEWED，作业失效

任一前向步骤失败，Saga 逆序执行已完成步骤的补偿，使整体回到一致态（作业票回到 DRAFT 或保留在失败前状态并标记 ABNORMAL）。

五、补偿（回滚）逻辑

补偿遵循三条原则：

  1. 幂等：补偿可因重试多次执行，须以业务键（ticketId）去重，不产生副作用。
  2. 可逆：前向动作必须有对应补偿；如"批准作业"补偿为"回退到 REVIEWED 且作业失效"。
  3. 不破坏审计：补偿仅改作业票状态与占用资源释放，所有操作仍入审计日志（WORM），保留完整链路。
// safetyTicketService 补偿示例
@Component("safetyTicketService")
public class SafetyTicketService {

    public boolean compensateSubmit(Map<String, Object> ctx) {
        String id = (String) ctx.get("ticketId");
        Ticket t = repo.findById(id).orElse(null);
        if (t == null) return true;                  // 已删除，幂等返回
        if (t.getStatus() == TicketStatus.SUBMITTED) {
            t.setStatus(TicketStatus.DRAFT);         // 回到草稿
            repo.save(t);
        }
        return true;
    }

    public boolean compensateApprove(Map<String, Object> ctx) {
        String id = (String) ctx.get("ticketId");
        Ticket t = repo.findById(id).orElse(null);
        if (t != null && t.getStatus() == TicketStatus.APPROVED) {
            t.setStatus(TicketStatus.REVIEWED);      // 作业失效，回退审核态
            t.setEffective(false);
            repo.save(t);
        }
        return true;
    }
}

六、与业务状态机的配合

Saga 负责跨服务最终一致，业务状态机（Spring Statemachine）负责单服务内状态合法跃迁，两者职责分离：

Saga 步骤成功 → 调用 safety-svc 内部状态机执行 TRANSITION
                (如 SUBMITTED → REVIEWED，由状态机守卫校验)
  • Saga 不感知业务细节，只触发"服务方法"；
  • 状态机拦截非法跃迁（如 DRAFT → APPROVED 跳过审核），抛出 40901，Saga 触发补偿；
  • 人工审核/批准由用户操作触发对应 Saga 步骤（流程可暂停等待人工，Seata Saga 支持 Wait 状态 + 唤醒）。
// 审核步骤（人工唤醒）
public void review(String ticketId, String reviewerId, boolean pass) {
    // 状态机守卫：仅 SUBMITTED 可转 REVIEWED/REJECTED
    stateMachine.sendEvent(new ReviewEvent(ticketId, reviewerId, pass));
    // 通知 Saga 引擎继续/补偿
    sagaEngine.wakeUp(businessKeyOf(ticketId), Map.of("reviewPass", pass));
}

一、设计原则

  • 窄表宽列：以 time 为分区维，device_no / metric 为标签（tag），value + quality 为值。
  • 标签字典化：设备/指标元数据存业务库（mdm/device），时序库只存编码，避免宽表膨胀。
  • 超表分块：按时间（如 1 天）自动分块（chunk），热数据在高速存储、冷数据压缩/降采样。
  • 连续聚合：预计算 1min/5min/1h rollup，大屏与统计直接查聚合表，减负原始超表。
  • 只追加：时序数据为不可变事实，更新极少；点位修正走"补数"而非 UPDATE。

三、连续聚合（Continuous Aggregate）

预计算大屏与统计所需 rollup，避免实时扫描原始超表。

3.1 设备点位 5 分钟聚合

CREATE MATERIALIZED VIEW v_device_metric_5m
WITH (timescaledb.continuous) AS
SELECT
    tenant_id,
    device_no,
    metric,
    time_bucket('5 minutes', time) AS bucket,
    avg(value)  AS avg_val,
    max(value)  AS max_val,
    min(value)  AS min_val,
    count(*)    AS cnt
FROM ts_device_metric
GROUP BY tenant_id, device_no, metric, bucket;

-- 每 1 分钟刷新
SELECT add_continuous_aggregate_policy('v_device_metric_5m',
       start_offset => INTERVAL '1 hour',
       end_offset   => INTERVAL '1 minute',
       schedule_interval => INTERVAL '1 minute');

3.2 重大危险源 1 分钟聚合（供 B2 看板）

CREATE MATERIALIZED VIEW v_hazard_param_1m
WITH (timescaledb.continuous) AS
SELECT
    tenant_id, hazard_id, metric,
    time_bucket('1 minute', time) AS bucket,
    avg(value) AS avg_val, max(value) AS max_val,
    bool_or(is_alarm) AS has_alarm
FROM ts_hazard_param
GROUP BY tenant_id, hazard_id, metric, bucket;

SELECT add_continuous_aggregate_policy('v_hazard_param_1m',
       start_offset => INTERVAL '2 hours',
       end_offset   => INTERVAL '1 minute',
       schedule_interval => INTERVAL '1 minute');

3.3 环保/能碳小时聚合

CREATE MATERIALIZED VIEW v_env_1h
WITH (timescaledb.continuous) AS
SELECT tenant_id, point_id, category, metric,
       time_bucket('1 hour', time) AS bucket,
       avg(value) AS avg_val, max(value) AS max_val,
       bool_or(is_over) AS has_over
FROM ts_env_monitor
GROUP BY tenant_id, point_id, category, metric, bucket;

CREATE MATERIALIZED VIEW v_energy_1h
WITH (timescaledb.continuous) AS
SELECT tenant_id, enterprise_id, energy_type,
       time_bucket('1 hour', time) AS bucket,
       sum(value) AS total, avg(power) AS avg_power,
       sum(carbon_equiv) AS carbon_total
FROM ts_energy_meter
GROUP BY tenant_id, enterprise_id, energy_type, bucket;

SELECT time, metric, value, is_alarm

  AND time > now() - INTERVAL '1 hour'
ORDER BY time DESC;

SELECT time_bucket('1 minute', time) AS t, avg(value) AS v

  AND time BETWEEN $4 AND $5

SELECT point_id, count(*) FILTER (WHERE is_over) AS over_cnt,

GROUP BY point_id;

六、与业务库的关系

业务库(PostgreSQL)                时序库(TimescaleDB)
─────────────────                ───────────────────
mdm: 设备/危险源主数据     ──1:N──▶ ts_device_metric.device_no
device: 设备档案/健康       ──1:N──▶ ts_hazard_param / ts_location_track
monitor: 预警/阈值规则      ──关联──▶ ts_hazard_param (is_alarm 派生)
env: 监测点/排口           ──1:N──▶ ts_env_monitor.point_id
energy: 碳配额/核算         ──关联──▶ ts_energy_meter (carbon_equiv 汇总)
  • 主数据在业务库，时序只存编码：设备名/量程/责任人等从业务库 JOIN 获取，避免冗余。
  • 告警派生：monitor-svc 消费 iot.raw，比对阈值后写业务库 warning 表，同时可在时序写 is_alarm 便于检索。
  • 回溯联动：历史告警详情页同时查业务库（告警记录）+ 时序库（参数曲线）。

七、多租户与分区

  • 单园区私有化：tenant_id 可固定，超表仅按 time 分区即可。
  • SaaS 多园区：tenant_id 作为子分区键（见建表语句 partitioning_column），配合行级权限（JDBC Filter 注入 tenant_id）实现数据隔离。
  • 写入路径：iot-ingest-svc → Kafka iot.raw → 消费者批量 COPY/INSERT 落超表；批量写入降低 WAL 压力。
  • 读路径：大屏 ioc-svc 直查连续聚合视图，监控服务查原始超表（带时间下推）。

六、容灾切换流程（按场景）

6.1 场景一：单微服务故障（P2/P3）

1. 告警触发（Prometheus）→ 运维组确认
2. kubectl get pods 确认 CrashLoop / OOM
3. 自动：HPA/重启自愈；超时则：
   helm rollback chem-park -n chem-park-app --set services.<svc>.tag=<last-good>
4. 验证：/actuator/health + 冒烟接口
5. 业务组确认功能恢复，关闭事件

6.2 场景二：数据库主库失效（P1）

1. 总指挥启动 P1，技术组长定位（PG 流复制延迟/主库宕机）
2. 运维组提升备库为主（Patroni/流复制 failover）
3. 应用连接串经 Nacos 动态切换（无需重启）
4. 校验：最近 5min WAL 已应用（RPO 核查）
5. 若主库数据损坏：从最近全量 + WAL 增量恢复至临时实例，校验后切换
6. 业务组全量验证（安全/环保/应急核心链路）

6.3 场景三：K8s 集群级故障（P1）

1. 总指挥决策切换至同城灾备集群（备用 K8s）
2. 运维组：备集群 helm upgrade 拉起全套（复用镜像仓库）
3. 恢复最新备份至备集群 DB（RPO 核查）
4. DNS/Ingress 切换至备集群入口（或 Gateway 权重切流）
5. 边缘网关重连备集群，积压数据补传
6. 大屏/移动端验证，业务组确认

6.4 场景四：安全事件（越权/入侵）

1. 安全组研判，冻结可疑账号（iam-svc 强制下线）
2. 网络组收紧 NetworkPolicy，隔离异常 Pod
3. 审计组导出 audit.log 留存证据（WORM）
4. 修复漏洞 → CI/CD 重发镜像 → 滚动替换
5. 复盘并补强规则（Sentinel/WAF）

ADR-001 微服务拆分边界（DDD 业务域）

  • 状态：已采纳（Accepted）
  • 背景：原型含 10 模块 46 界面，业务跨度大（安全/环保/应急/能碳/管廊/运营）。单体架构无法满足"分期交付、独立扩容、故障隔离"，且高频监测会拖垮台账类业务。
  • 决策选项： 1. 单体应用（快速但耦合高，否决） 2. 按技术层拆分（gateway/dao/service，否决：业务仍耦合） 3. 按业务域（DDD）拆分为 14 个服务（采纳）
  • 最终决策：按 DDD 业务域拆分为 14 个微服务，每服务独立库、单一职责。将 monitor 与 device、emergency 独立隔离。
  • 后果：
  • 优点：职责清晰、可独立部署扩容、故障隔离、对齐分期交付。
  • 代价：分布式事务/运维复杂度上升（由 ADR-003/010 缓解）。

ADR-002 服务间通信：同步 Feign + 异步 Kafka 双通道

  • 状态：已采纳（Accepted）
  • 背景：页面查询需低延迟响应，跨域事件（告警/应急）需解耦削峰且不可丢。
  • 决策选项： 1. 全同步 REST（简单，但耦合高、无削峰，否决） 2. 全异步消息（解耦，但实时查询体验差，否决） 3. 同步 Feign（查询）+ 异步 Kafka（事件/数据流）双通道（采纳）
  • 最终决策：实时请求走 OpenFeign（经 Gateway，带熔断）；告警/预警/应急/数据流走 Kafka（保序、不丢、可重放）。
  • 后果：
  • 优点：兼顾实时性与解耦；Kafka 分区键保序，至少一次投递。
  • 代价：需维护两套通信语义；消费者幂等（eventId）必须实现。

ADR-003 分布式事务采用 Seata Saga

  • 状态：已采纳（Accepted）
  • 背景：作业票审批、隐患整改等跨多服务长流程，需最终一致且可补偿（驳回/退回修改）。2PC 会长期持锁拖垮高频监测库。
  • 决策选项： 1. 2PC/XA（强一致但持锁久，否决） 2. TCC（性能好但侵入强，适合短资源锁定） 3. Saga（长流程补偿，采纳）；TCC 仅用于应急资源锁定
  • 最终决策：跨服务长流程用 Seata Saga（前向+补偿），状态机守卫单服务状态跃迁；应急资源锁定用 TCC。
  • 后果：
  • 优点：最终一致、不长期持锁、业务可驳回回滚。
  • 代价：补偿逻辑需幂等设计；需 Saga 可视化与死信运维。

ADR-004 IOC 大屏采用 CQRS 只读聚合

  • 状态：已采纳（Accepted）
  • 背景：IOC 综合态势一张图需聚合安全/环保/应急/能源/物流五域数据，30s 刷新、≤5s 加载，且要"平急结合"秒级切换。
  • 决策选项： 1. 大屏直连各业务库（耦合高、影响业务库性能，否决） 2. 独立 ioc-svc 只读聚合（CQRS 读侧）：订阅事件 + 主动拉取组装（采纳）
  • 最终决策：ioc-svc 不持有业务真相源，仅订阅 Kafka 告警事件 + Feign 拉取各域摘要写入本地聚合缓存，大屏只读该服务。
  • 后果：
  • 优点：业务库零压力、大屏高性能、切换快。
  • 代价：聚合数据有秒级延迟；需处理缓存失效与降级兜底。

ADR-005 时序数据采用 TimescaleDB

  • 状态：已采纳（Accepted）
  • 背景：IoT 点位、重大危险源参数、环保监测等高频写入（10s 刷新）且需长期历史回溯、趋势统计。
  • 决策选项： 1. 纯关系表（写入/查询性能差，否决） 2. 纯时序库（如 InfluxDB，但与 PostgreSQL 生态割裂、多租户复杂，否决） 3. TimescaleDB（PostgreSQL 扩展，兼容 SQL + 超表 + 连续聚合）（采纳）
  • 最终决策：业务关系数据用 PostgreSQL，高频时序数据用 TimescaleDB 超表 + 连续聚合 + 压缩降采样。
  • 后果：
  • 优点：SQL 统一、运维简单、聚合视图减负、压缩比高。
  • 代价：需独立管理超表保留/压缩策略；与业务库备份需协调。

ADR-006 注册中心与配置中心统一采用 Nacos

  • 状态：已采纳（Accepted）
  • 背景：需服务发现、动态配置、多环境隔离，并尽量降低组件数量。
  • 决策选项： 1. Eureka + Config + Bus（组件多，否决） 2. Consul（功能全但团队熟悉度低，备选） 3. Nacos（注册+配置一体，国产、云原生友好）（采纳）
  • 最终决策：统一采用 Nacos 作为注册中心与配置中心（Namespace 环境隔离、Group 服务隔离、敏感配置加密）。
  • 后果：
  • 优点：组件收敛、动态刷新、国产合规。
  • 代价：Nacos 自身需集群高可用（≥3 节点）；注册中心抖动依赖本地缓存降级。

ADR-007 应急指挥服务独立高可用隔离域

  • 状态：已采纳（Accepted）
  • 背景：应急是"平急结合"指挥中枢，事故响应"黄金十分钟"要求调度不被日常流量/外部依赖拖垮。
  • 决策选项： 1. 应急作为普通业务服务（故障会阻断调度，否决） 2. emergency-svc 独立部署单元 + 高优先级 + 降级兜底 + 本地预案基线（采纳）
  • 最终决策：emergency-svc 独立资源配额（priorityClass high-priority，多副本，反亲和）；对其他域调用均带熔断降级，本地缓存预案/资源基线。
  • 后果：
  • 优点：应急链路韧性最强，外部不可用仍可调度。
  • 代价：需维护基线数据一致性；资源成本略高。

ADR-008 安全合规遵循等保 2.0 三级内建

  • 状态：已采纳（Accepted）
  • 背景：BRD 明确要求等保 2.0 三级；化工园区属关键信息基础设施相关场景。
  • 决策选项： 1. 上线后补安全（测评风险高，否决） 2. 安全左移、内建于架构各层（采纳）
  • 最终决策：传输 TLS 1.3、存储 AES-256/TDE、三级 RBAC + 行级多租户、审计 WORM、网络隔离（NetworkPolicy）、三员分立。
  • 后果：
  • 优点：测评可顺利通过，安全可验证。
  • 代价：部分性能开销（加密/审计）；需持续合规运营。

ADR-009 API 网关统一鉴权与限流

  • 状态：已采纳（Accepted）
  • 背景：多端（Web/大屏/移动/企业/监管）接入，需统一入口做认证、鉴权、限流、灰度。
  • 决策选项： 1. 各服务自理鉴权（重复、易漏，否决） 2. Spring Cloud Gateway 统一鉴权 + Sentinel 限流 + 灰度（采纳）
  • 最终决策：所有外部请求经 Gateway，校验 OAuth2.1 token、解析三级权限、按服务维度限流；紧急态 emergency 路由最高优先级。
  • 后果：
  • 优点：安全边界清晰、限流防雪崩、灰度可控。
  • 代价：网关成为关键路径，需高可用（多副本 + 熔断）。

ADR-010 容器化部署采用 Kubernetes + Helm

  • 状态：已采纳（Accepted）
  • 背景：14 服务 + 中间件需标准化交付到私有化/政务云集群，支持滚动升级、弹性伸缩、故障自愈。
  • 决策选项： 1. 物理机/虚拟机手工部署（慢、易错，否决） 2. Kubernetes + Helm 标准化部署（采纳）
  • 最终决策：全部容器化，K8s 编排，Helm Chart 一键部署；HPA 自动扩缩、Pod 反亲和、NetworkPolicy 隔离。
  • 后果：
  • 优点：交付快、可复制（多园区 SaaS）、自愈能力强。
  • 代价：集群运维门槛；需镜像仓库与 CI/CD 配套（见 CI/CD 文档）。

ADR-011 多租户隔离策略（Schema / 库 + 行级）

  • 状态：已采纳（Accepted）
  • 背景：平台既可能单园区私有化，也可能多园区 SaaS；需数据隔离且兼顾成本。
  • 决策选项： 1. 共享表无隔离（安全隐患，否决） 2. 单园区：Schema 隔离；SaaS 多园区：库/实例隔离 + 行级 tenant_id 过滤（采纳）
  • 最终决策：按部署模式选择——私有化按 Schema 隔离（每园区/企业独立 Schema）；SaaS 按实例 + 行级 JDBC Filter 注入 tenant_id。
  • 后果：
  • 优点：隔离强度可调，灵活适配两种交付。
  • 代价：SaaS 模式需中间件（MyCat/ShardingSphere）或 Filter 统一管控，避免越权。

ADR-012 部署与交付分期对齐产品路线图

  • 状态：已采纳（Accepted）
  • 背景：路线图分三期（M1–M36），模块优先级 P0>P1>P2；需架构支撑分期上线而非一次性交付。
  • 决策选项： 1. 一次性全量交付（风险高、周期长，否决） 2. 服务按优先级分批上线，对齐 Phase 1/2/3（采纳）
  • 最终决策：Phase1 上线 iam/mdm/iot-ingest/device/safety/monitor/closedmgmt/ioc/gateway + 数据中台基础；Phase2 补 env/energy/emergency 补全/ioc 升级；Phase3 补 operation/corridor/AI。
  • 后果：
  • 优点：合规达标先行、风险可控、投资分期。
  • 代价：前期服务需预留后期接口与事件契约兼容性（向后兼容演进）。
